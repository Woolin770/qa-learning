# 测试级别、类型与模型（2026-11-03）

## 1. 四个测试级别
| 级别     | 谁做      | 测什么                                           | 依据什么文档                     |
| -------- | --------- | ------------------------------------------------ | -------------------------------- |
| 单元测试 | 开发      | 程序源代码                                       | 软件详细设计文档、模块规格说明书 |
| 集成测试 | 开发/测试 | 模块之间的**接口与数据交互**、调用顺序           | 软件概要设计文档、接口设计文档   |
| 系统测试 | 测试      | 功能、兼容、文档等                               | 软件需求规格说明书               |
| 验收测试 | 用户      | 验证系统**是否满足业务需求和验收标准**、能否上线 | 需求文档、用户手册、验收标准     |

## 2. 六种测试类型（每种一句话 + 什么时候用）
| 类型 | 一句话解释                                                   | 什么时候用                                                   |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 功能 | 验证软件各个功能是否按照需求规格说明正常工作                 | 在功能开发完成后，用于确认基本业务流程和具体功能点是否符合需求。 |
| 性能 | 测试系统在不同负载（如并发量、数据量）下的响应速度、稳定性和资源消耗情况 | 在系统上线前或面临大促（如秒杀活动）时，用于发现系统瓶颈并确保满足性能指标 |
| 兼容 | 验证软件能否在不同的操作系统、浏览器、设备型号及网络环境下正常运行 | 在产品面向大众发布前，特别是移动端应用或Web前端，用于确保不同用户环境下的使用体验一致。 |
| 安全 | 检查系统的防侵入能力，确保用户数据、账户权限及交易信息不被非法获取或篡改 | 涉及用户隐私、支付交易等敏感数据的系统，在版本更新或面临安全审查时，用于防止数据泄露和恶意攻击 |
| 易用 | 评估软件的界面布局、操作流程是否符合用户习惯，是否简单易懂   | 在产品原型阶段或新功能上线前，通过观察真实用户操作，用于发现交互障碍并优化用户体验 |
| 接口 | 测试系统内部模块之间或与外部系统交互的数据传递、逻辑处理是否正确 | 在后端开发完成后、前端界面未完成时，用于提前验证业务逻辑、数据结构及错误处理机制 |

## 3. V 模型与 W 模型
- V 模型：左边开发四级、右边测试四级，一一对应。最大缺点：___测试过程是软件生命周期的最后一部分，测试后置：需求/设计阶段的问题要到系统测试才暴露，返工成本高___
- W 模型：测试与开发并行，需求一确定就开始设计验收用例。核心思想：___尽早的进行软件测试___
- 一句话区别：___测试是否伴随软件的整个生命周期___

## 4. 冒烟 vs 回归（最容易混）
|              | 冒烟测试                                                     | 回归测试                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 目的         | 验证新版本的核心主流程是否通，判断是否具备后续深入测试的条件 | 代码修改后，**原有的**正常功能没被破坏                       |
| 时机         | 开发完成并提交新版本后，正式全面测试开始之前                 | 在开发修复bug后，新功能开发完成后或代码重构后                |
| 范围         | **非常小**。仅覆盖最核心的业务主流程                         | **比较大**。覆盖所有受本次变更影响的相关模块，以及核心既有功能。 |
| 不通过怎么办 | 直接打回                                                     | 提交缺陷                                                     |

## 5. 六维度练习：登录功能
 功能：正确账号密码能登录；连续登录3次都能成功

 性能：多人同一时间点击登录会不会卡死；网络较差状态下的响应

 兼容：Chrome / Edge / Safari / Firefox + iOS / Android；手机分屏状态按比例缩放

 安全：密码加密传输；能否暴力破解

 易用：回车键是否可以直接提交登录；Tab 顺序、回车提交、密码可见切换、错误提示位置、输入框自动聚焦

 接口：直接调 `/login` 传空密码、超长密码、SQL 注入，看**后端**是否校验；返回的状态码和字段是否符合契约；

## 7. 自测（明天抽查）
1. 单元测试为什么不是测试人员做？

   开发自己在编写代码的时候会对代码进行测试

2. V 模型最大的缺点？

   测试后置

3. 冒烟不通过怎么处理？

   直接打回

4. 改了「优惠券规则」，做回归还是冒烟？为什么？

   回归，只是已有功能修改

5. 验收测试和系统测试的边界在哪？

   系统测试和验收测试的核心边界在于**验证视角**和**最终目的**的不同：系统测试（ST）是由测试工程师在测试环境中，依据技术规格书验证产品“有没有缺陷”和“符不符合需求”，而验收测试（UAT）则是由客户或业务方在准生产环境中，通过模拟真实业务场景确认产品“是不是我想要的”以及“能不能满足实际使用要求”；简单来说，前者是技术把关的“质量验收”，后者是业务签字的“交付确认”。
